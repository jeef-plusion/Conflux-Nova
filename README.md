# 第一部分 · 架构思想（Conflux Nova Neo 2.0.0-Core）

## 1.1 立项推论：内核与计算图是同一样东西

从物理本质讲，所谓「计算内核」与「计算图」最后都变成一条条指令。既然如此，我们就没必要为它们各建一层抽象。

这条推论直接决定了后面所有设计：**没有 graph 层，没有 op 注册表，没有运行期分派**——内核就是图。

传统推理引擎反其道而行：为了让所有硬件都能算什么，不得不在运行期判断模型架构、张量类型、该走哪个 kernel。

我们选择**在编译期把模型焊死**：一个二进制只服务一个模型，所有形状都是常量，所有分支在编译期消失。代价是模型面窄，换来的是内核里没有一处 `switch`。

## 1.2 六段契约

```
INPUT_CHAT → INPUT_TOKENIZR → INPUT_START →（计算）→ OUT_TKZ → OUT_chat → OUT_OUT
```

每一段是一个文件、一个全局函数。**处理完直接唤醒下一段**，没有调度器，没有注册表，没有基类。

| 段 | 职责 | 出口 |
|---|---|---|
| `INPUT_CHAT` | 收用户输入，套聊天模板 | 调 `INPUT_TOKENIZR` |
| `INPUT_TOKENIZR` | 文本 → token（词表在这一段） | 调 `INPUT_START` |
| `INPUT_START` | 计算侧针脚，只吃 token id | 每出一个 token 触发 `OUT_TKZ` |
| `OUT_TKZ` | token → 字节，切完整 UTF-8 前缀 | 调 `OUT_chat` |
| `OUT_chat` | 去特殊标记、清洗 | 调 `OUT_OUT` |
| `OUT_OUT` | 落终端 / 落 socket / 落任何地方 | 收尾 |

所以我们接受的贡献是**模块**，不是新架构：任意一段都可以被替换，只要它还叫这个名字、还在结尾唤醒下一段。

## 1.3 技术特点

### 1.3.1 模块化设计

在我们的架构中，有一批文件的命名遵循「大写 + 下划线」的格式——它们本质上就是**模块**。

传统架构把词表和聊天模板嵌在内部，想单独改一处十分困难。我们直接把它们拆成独立文件；使用时，模块的入口是一个函数，参数由文件自己构造。

这给了开发者极大的自由，同时明确了分工：对不同领域有不同擅长的人，完全可以提供自己的逻辑，在编译时由他人复用、自行编辑参数。

### 1.3.2 计算物理化

传统通用计算里，所有人都在干一件事：**让所有硬件都能计算**。

但这句话被忽略了一个宾语——计算什么？算 fp16，还是算 transformer？

**计算这件事，从来没被自己论证过。**

我们把硬件的能力指数设为一个函数 `v(d)`，数据为参数 `d`，总任务量为 `s`，则：

```
T = s / v(d)
```

`d` 非常复杂，要结合数据量、数据类型、数据格式。而现代计算机本身就是有**针对性**的：浮点数在不同设备上的运算效率完全不同，不同硬件的组织方式也完全不同。

由此我们得到 `d` 的定义域。这看似浅显，但能推出一个更直接的结论：

> **`v(d)` 在其能力范围内，闭区间 `[0, q]` 才是该函数单调性增长的唯一区间。**

举一个例子就够了：一个 64 位 CPU，你给它一堆「每块 13 字节」的数据，或者「每块 250 字节」的数据，你试试？

这为我们定下了一条适配路线：**对硬件心里有数，而不是靠猜。** 每一次硬件适配，必须先综合评价硬件的极限能力和底线。

有人会说：这违背了「让硬件自由接入」的初心。我们认为是错的。

商业上也有完全对应的例子：采购设备是根据需求来的。一个普通人不需要 H100，RTX 5090 就是天花板级别了；你再强，也不会有人选，除非它更便宜。

所以落到这张卡上：1080 Ti 只有 11 GB 显存，超过 11 GB 就溢出到内存，此时计算极低效，体验完全谈不上。它凭什么去跑 27B？用 Q2 这种级别的量化，跑出来的东西能用吗？那还不如直接跑一个 1.5B 的低量化。

在我们的架构里，**适配一个模型不再看它的名字，而是看它的实际实力。**

### 1.3.3 量化底线：Q4_K_M

既然要在 1080 Ti 上跑，就必须先确立一条线：**什么级别的量化才能保证模型是能用的，而不是勉强能用的。**

我们要让硬件「能用」，而不是「勉强能用」。几 token/s 的垃圾数据不叫优化。

所以定下一条硬规矩：**Q4_K_M 是入库下限。低于 Q4_K_M 的优化一律不入库。**

| 档位 | 结论 |
|---|---|
| Q4_K_M 及以上 | ✅ 黄金标准，精度保留 95% 以上，允许 |
| Q4_K / Q4_0 / Q3 以下 / Q2 | ❌ 不入库 |

在这个前提下，这张卡的实用上限也随之确定：**14B + Q4_K_M + 上下文 ≤ 8K** 是稳定边界；再往上就是 Q2 级别的垃圾输出，不如直接跑 1.5B 的低量化。

### 1.3.4 计算的绝对黑盒性（仅针对前端与应用层）

传统架构里做一个 AI 应用极其复杂：要调这个、要调那个，还不清楚它到底怎么跑。而在这里，你可以在完全不清楚计算细节的情况下直接跑起来。

我们把「接入计算」的成本压缩成了一个文件里的 `OUT_OUT`。

一个编译版本里可以内嵌特别多硬件后端，而这些后端你可以直接从硬件开发者和内核开发者手里拿到他们的库，然后调用我们的全局函数 `OUT_OUT`，就可以把你的东西直接提交给他们（前提当然是有相同的初始化条件）。

在保证了计算的绝对黑盒性之后，上层想怎么玩，随便怎么玩。

### 1.3.5 KV cache 块协议（设计）

我们给 AI 的每一次输出都编一个 KV cache 块。整体逻辑是：

- **前缀** = 该对话第一次输入量化之后的 ID；
- **后缀** = 该次对话 KV cache 增量的量化 ID。

这样划分的好处是：每一句话是一个基本单位，AI 输出的每一次结果也是一块。人说的话一般比 AI 少，记忆的绝大部分由 AI 的输出占据，而「字」就是最基本的分割单位。

这样划分之后，计算时可以由用户自己决定使用哪些记忆块，从而实现对记忆的高度修改——这在角色扮演里是一件利器。

**命名规格**：`[首次输入向量 24 位哈希].[该 KV 块 24 位哈希]`

```
Kv_block = { AFFAA1891C2A31DAC16958AC . 618649689ACDE6187F681AA2 }
```

命名不用运行期参数，而用哈希：会有一点额外开销，但它是跨对话复用与删改记忆最稳的办法。

后继修订：改为对「编码后的 UTF-8 数字序列」做完整加权——权重取值范围 ±(长度/2)，用整除逐级取位把结果压到 24 位内，再按位置加权得到最终 ID；模型输出侧则把「输出哈希 ID」与「增长的 KV 块」绑定。

> 状态：架构层面已定稿，代码尚未实现（`Session` 中暂无块表）。

## 2.4 实测

| 场景 | 单路 | 聚合 |
|---|---|---|
| 7B 单路，ctx 2048 | — | 53~55 tok/s |
| 7B 四路批量，KV≈100 | 26.1 tok/s | **104.5 tok/s** |
| 7B 四路批量，KV≈220 | 15.4 tok/s | 62 tok/s（P2 归一） |
| 3 路批量，KV≈300 | 26.7 tok/s | 80 tok/s |
| 1.5B 四路批量，KV≈290 | 75.9 tok/s | **303 tok/s** |
| 7B prefill（2048 tok） | — | 536 tok/s |

> 这张卡会掉 P5（734/810 MHz），同一份代码能测出 18 ms 和 143 ms 两种结果。以上数字均在 `nvidia-smi` 记录到 SM 1690~1847 MHz / MEM 5508 MHz 时采集，P5 数据已按频率归一。

### 物理边界：不同 KV 长度下的聚合吞吐 (GTX 1080Ti)

```
7B   · 4 路 · KV≈100   ███████████████████████████████████████   104.5 tok/s
7B   · 3 路 · KV≈300   ██████████████████████████████             80.0 tok/s
7B   · 4 路 · KV≈220   ███████████████████████                    62.0 tok/s
1.5B · 4 路 · KV≈290   ██████████████████████████████████████████████████████████████████████████████████████████████████████████  303.8 tok/s
```

| 场景 | KV 长度 | 单路 | 聚合 | 说明 |
|---|---|---|---|---|
| 1.5B · 4 路 | ≈290 | 75.9 tok/s | **303.8 tok/s** | 小模型吃满带宽 |
| 7B · 4 路 | ≈100 | 26.1 tok/s | **104.5 tok/s** | 短对话，attention 便宜 |
| 7B · 3 路 | ≈300 | 26.7 tok/s | **80.0 tok/s** | 少一路，但上下文更长 |
| 7B · 4 路 | ≈220 | 15.4 tok/s | **62.0 tok/s** | 长上下文，attention 开始收税 |

**结论**：decode 受带宽约束，gemv4 让 4 路共享一次权重读取，所以聚合能超单路；但 attention 的成本随 KV 线性增长，上下文越长，聚合越接近单路的物理上限。短上下文是并发的甜蜜区。
